# API Key 安全策略

本文档说明 Screenshot AI 如何保护你的 API Key、截图数据会流向哪里，以及在什么情况下这些保护会失效。

> **一句话结论**：API Key 在设备本地用 Android Keystore 主密钥做 AES256-GCM 加密后存储，
> 明文永不落盘，也绝不离开设备（除了发往你自己配置的那家模型厂商）；
> **截图会被发送到该厂商** —— 这是应用的工作原理，不是缺陷。

## 密钥是怎么存的

### 存储链路

```text
用户在设置页粘贴 API Key
        │
        ▼
┌───────────────────────────────────────────────────────────┐
│ 1. Android Keystore 生成/取回主密钥 MasterKey             │
│    · 密钥材料由 TEE / StrongBox 硬件保护，不可导出        │
│    · 别名固定（如 screenshot_ai_master_key）              │
│    · AES256-GCM，GCM 自带完整性校验                       │
├───────────────────────────────────────────────────────────┤
│ 2. EncryptedSharedPreferences 用主密钥加密                │
│    · 键名与键值分别加密                                   │
│    · 每次写入使用新的随机 IV（nonce），杜绝 IV 重用        │
├───────────────────────────────────────────────────────────┤
│ 3. 密文写入应用私有 SharedPreferences                     │
│    /data/data/com.screenshot.ai/shared_prefs/...          │
│    · 其他应用无 root 无法读取                             │
└───────────────────────────────────────────────────────────┘
        │
        ▼
   仅在使用时于内存中解密 → 拼进 HTTPS 请求头 → 随请求结束释放
```

### 关键性质

| 性质 | 说明 |
| --- | --- |
| **明文不落盘** | 磁盘上只有密文；`adb backup`、文件管理器、第三方备份工具拿到的都是密文 |
| **硬件级保护** | 主密钥由 TEE / StrongBox 持有，**即使把 `/data` 分区整个复制走也无法解密** |
| **完整性校验** | GCM 模式同时提供机密性与完整性，密文被篡改会解密失败而非静默返回错误值 |
| **不可导出** | 主密钥标记为不可导出（non-exportable），应用自身也无法读出密钥字节 |
| **随机 IV** | 每次加密都生成新的随机 IV，避免 GCM 在 IV 重用下的灾难性失效 |
| **界面不回显** | 设置页只显示掩码（如 `sk-••••••••1a2b`），不提供「查看明文」按钮 |

### 与「直接存 SharedPreferences」的对比

```kotlin
// ❌ 绝对禁止的写法：明文存盘
prefs.edit().putString("api_key", key).apply()

// ❌ 同样禁止：自研「加密」（硬编码密钥/简单异或/Base64 混淆）
val obfuscated = Base64.encodeToString(key.xor(0x5A), NO_WRAP)

// ✅ 本项目采用：Keystore 主密钥 + AES256-GCM + EncryptedSharedPreferences
encryptedPrefs.edit().putString("api_key_$providerId", key).apply()
```

> 自研加密的问题在于**密钥本身也要存在某处**，最终退化成一个静态字符串，
> 反编译一次就全暴露了。Keystore 的价值就在于密钥**根本不以字节形式存在于任何地方**。

### 已知局限

- `androidx.security:security-crypto`（EncryptedSharedPreferences 的实现库）已被上游标记为
  不再积极演进。但**「用 Keystore 主密钥加密后再存盘」这一安全模式本身依然是 Android 官方的
  推荐做法**，即便将来更换具体库，架构也不会变。
- 加密保护的是**静态数据（at rest）**。应用进程运行期间，Key 必然以明文形式存在于内存中 ——
  这是任何客户端的固有属性，无法规避。

## 为什么禁用云备份

`AndroidManifest.xml` 中设置了：

```xml
<application
    android:allowBackup="false"
    android:fullBackupContent="false"
    android:dataExtractionRules="@xml/data_extraction_rules" ... >
```

原因有三层：

### 1. 密文备份到云端，等于把攻击面搬到云端

Keystore 主密钥**不会**随备份迁移（它绑定设备）。这带来两个后果：

- 换机恢复后密文无法解密 —— 备份本身**没有实际价值**（用户还得重新填 Key）；
- 但如果 Google 账号被攻破，攻击者拿到的是**一堆密文 + 完整的截图历史**，
  其中截图历史的危害可能比 Key 更大（截图里可能有聊天记录、身份证、验证码）。

**即「备份」在这里收益为零、风险为正。**

### 2. 截图历史的备份是一颗定时炸弹

`filesDir/screenshots` 与 Room 数据库里存着用户历次截取的屏幕内容。
这些内容一旦进入云备份，就脱离了应用的控制范围：

- 备份可能在用户不知情的情况下同步到多台设备；
- 备份的保留策略由操作系统与云服务商决定，应用无法删除；
- 用户清理应用数据后，备份中的副本**依然存在**。

### 3. 减少合规与信任成本

禁用备份是最简单、最彻底的做法：**数据要么在设备上，要么被删掉，不存在第三种状态。**
用户不需要理解「云备份里到底存了什么」，因为答案就是「什么都没存」。

> 换机的正确做法：在新机上重新填入 API Key（几十秒），截图历史不迁移。
> 我们宁可让你多花半分钟，也不愿让敏感截图躺在云端。

## 威胁模型

我们**保护什么**、**防范谁**、以及**哪里防不住**，全部明说。

### 防护目标

| 资产 | 敏感程度 | 说明 |
| --- | --- | --- |
| API Key | 🔴 高 | 泄露 = 他人可用你的额度消费（部分厂商 Key 还能改配置） |
| 截图原图 / 历史记录 | 🔴 高 | 可能包含聊天记录、证件、验证码、工作机密 |
| 发送给模型的 Prompt 与回答 | 🟠 中 | 由厂商侧留存策略决定 |

### 威胁矩阵

#### ✅ 能防住

| 威胁 | 防护手段 |
| --- | --- |
| 手机上其他普通应用读取 Key 或截图 | Android 应用沙箱 + 私有目录；无 root 无法跨应用读 `/data/data/...` |
| 手机丢失后被离线取证 | Keystore 硬件保护 + GCM 完整性校验，密钥不可导出 |
| `adb backup` 拖走应用数据 | `allowBackup="false"`，备份通道直接关闭 |
| 截图意外进入相册被其他应用扫描 | 只写 `filesDir/screenshots`，从不调用 MediaStore |
| 中间人窃听请求 | 全程 HTTPS，依赖系统 CA 体系做证书校验 |
| 日志泄漏 Key | 代码规范禁止打印 Key 与 Base64，Review 环节强制检查 |

#### ⚠️ 防不住 / 有条件的

| 威胁 | 为什么防不住 | 缓解建议 |
| --- | --- | --- |
| **已 root 的设备** | root 可读取任意应用私有目录，也可注入进程内存抓取解密后的明文 Key | 不要在已 root 的主力机上使用；或改用额度受限的子 Key |
| **恶意应用（无障碍/注入）** | 无障碍服务可读取屏幕内容、模拟点击；Xposed/Frida 类框架可 Hook 解密函数 | 只从可信来源安装应用；定期检查无障碍服务列表 |
| **用户主动分享截图** | 截图是用户自己发出去的 | 结果小窗提供复制的是**文本**，不含原图 |
| **厂商侧留存** | 数据一旦离开设备就受该厂商隐私政策约束 | 选择隐私政策清晰、支持关闭训练的厂商；不要发送敏感画面 |
| **中转/代理网关** | Base URL 指向的中转方能同时看到 Key 与全部请求内容 | 优先直连官方；必须中转时自建可审计网关 |
| **调试版被逆向** | 反编译可看到业务逻辑（但看不到 Keystore 里的密钥） | 正式使用请装 Release 包；开源代码本就公开，逻辑无秘密 |
| **系统级备份（厂商云服务）** | 部分国产 ROM 的整机备份行为不完全受 `allowBackup` 约束 | 关闭系统云同步中的该应用；或在设置中排除 |

#### ❌ 明确不在防护范围

- **屏幕本身被他人看到**（肩窥）—— 这是物理安全问题。
- **你主动把 Key 粘贴到聊天软件里** —— 社交工程，技术手段无法阻止。
- **厂商侧数据泄露** —— 完全取决于厂商的安全能力，本项目无从干预。
- **受保护界面（`FLAG_SECURE`）** —— 系统禁止截屏，这不是安全边界，只是功能限制。

### 特别说明：无障碍服务权限

本项目使用无障碍服务（`canTakeScreenshot="true"`）实现截图。这是一个**权限很高的服务**，
我们明确承诺它的用途范围：

- ✅ 只用于调用 `takeScreenshot()` 获取屏幕位图；
- ❌ 不读取界面节点树（不解析你在看什么内容）；
- ❌ 不模拟点击、不注入按键、不监听输入；
- ❌ 不在后台被动采集屏幕。

由于代码完全开源（GPLv3），**以上承诺可以自行审计验证** —— 这正是选择开源的理由之一。

## 截图数据流与隐私边界

### 数据流向图

```text
                    ┌──────────────── 设备内 ────────────────┐
 屏幕画面 ──截图──▶ │ filesDir/screenshots（应用私有目录）    │
                    │        │                                │
                    │        ├─▶ Room 历史库（缩略图/路径）    │
                    │        │                                │
                    │        └─▶ ImageUtils 压缩 ──▶ Base64    │
                    │             或 OcrUtils(ML Kit) ──▶ 文本 │
                    └───────────────────┬─────────────────────┘
                                        │  HTTPS（仅当你使用 AI 功能时）
                                        ▼
                    ┌──────────── 你配置的那家厂商 ────────────┐
                    │  DeepSeek / OpenAI / Gemini /            │
                    │  Anthropic / 通义千问 / 豆包              │
                    │  · 按该厂商隐私政策处理与留存             │
                    └──────────────────────────────────────────┘

  ⛔ 本项目不存在的链路：作者服务器 / 中转服务器 / 统计 SDK / 广告 SDK / 崩溃上报 SDK
```

### 逐条说清楚

| 问题 | 答案 |
| --- | --- |
| 截图存在哪？ | 应用私有目录 `filesDir/screenshots`，以及 Room 数据库中的历史记录 |
| 会进相册吗？ | **不会**。全程不调用 `MediaStore`，不申请任何存储权限 |
| 其他应用能看吗？ | 不能（无 root 情况下沙箱隔离） |
| 会上传到作者服务器吗？ | **不会**，本项目没有服务器 |
| 会上传给模型厂商吗？ | **会**。这是应用的工作方式：视觉模型收到 Base64 图片，非视觉模型收到本地 OCR 文本 |
| 有埋点/统计/崩溃上报吗？ | **没有**。除 `ai/net/` 发往你所配置厂商的请求外，无任何出网行为 |
| 有账号体系吗？ | **没有**。不需要注册、登录，不采集任何设备标识 |
| 删掉历史就真删了吗？ | 是。删除会同时清理数据库记录与对应文件（如有遗漏请提 Issue，这属于 bug） |

### 边界声明（请务必理解）

> ⚠️ **截图一旦发送给模型厂商，就脱离了本项目的控制范围。**
> 厂商是否留存、留存多久、是否用于模型训练，完全由其服务条款与隐私政策决定，
> **本项目无法干预、无法审计、也无法代为删除**。
>
> 因此：**不要用本应用截取并发送身份证、银行卡、密码、验证码、医疗记录、商业机密等敏感内容。**
> 这不是应用的限制，而是「把画面交给第三方大模型」这件事本身的固有风险。

## 用户可以做的加固

按投入产出比排序：

### 1. 使用额度受限的独立 Key（最推荐）

到厂商控制台**专门为本应用创建一个 Key**，不要复用主账号 Key：

- DeepSeek / OpenAI / 通义千问 / 火山方舟都支持创建多个 Key；
- 给该 Key 设置**月度消费上限或告警**；
- 一旦怀疑泄露，**单独吊销这一个 Key**，不影响其他用途。

即使 Key 最终泄露，损失也被限制在一个可控金额内。

### 2. 定期轮换 Key

建议每 **3~6 个月**更换一次。到厂商控制台创建新 Key → 填入 App → 删除旧 Key。
删除旧 Key 后，即使它曾被复制走也已经失效。

### 3. 不要在已 root / 越狱 / 装有 Xposed 的设备上使用

root 会彻底瓦解 Android 的沙箱与 Keystore 隔离假设。如果必须使用：

- 换用额度极小的 Key；
- 或考虑只在非 root 的备用机上使用本应用。

### 4. 检查无障碍服务列表

定期查看 设置 → 无障碍 → 已安装的服务：

- 只保留你信任的服务；
- 任何**不认识的服务都应立即关闭并卸载其来源应用**（恶意无障碍服务是 Android 上最危险的威胁之一）。

### 5. 保持系统与应用更新

- 系统安全补丁会修复 Keystore、TEE、WebView 等组件的漏洞；
- 本应用的新版本会修复已知问题，请通过 Releases 页面获取更新。

### 6. 谨慎使用自定义 Base URL

中转方能同时看到**你的 Key** 和**每一次请求的完整内容（含截图）**：

- 优先直连官方端点；
- 必须中转时，优先选择可自建、可审计的开源网关（如 one-api、LiteLLM）；
- 绝不要把公司主账号的高权限 Key 交给第三方中转。

### 7. 及时清理历史

历史记录会占用私有目录空间，长期留存也增加敏感信息暴露面。
在历史页定期清理不再需要的记录。

### 8. 关闭不必要的开机自启

如果你不是每天都在用，建议在设置页**关闭开机自启** ——
减少后台常驻时间，也就减少了潜在的攻击窗口。

### 9. 用低质量模式减少信息暴露

低质量模式把图片长边压到 **512px**。除了省钱，还有一个安全上的副作用：
**细节更少，敏感信息更不容易被完整识别**（当然，这不能替代「不要发敏感内容」的原则）。

### 10. 安装来自可信来源的 APK

- 优先从本仓库的 **Releases** 页面下载；
- 或**自行编译**（`./gradlew :app:assembleDebug`）—— 这是最可信的方式；
- 警惕第三方站点二次打包的 APK，它们可能被注入了额外的收集代码。

## 开发者必须遵守的规则

如果你要为本项目贡献代码，以下几条是**硬性要求**，违反的 PR 会被直接拒绝：

1. **禁止**以任何形式打印 API Key、截图 Base64、完整请求体到日志。
   ```kotlin
   // ❌ 禁止
   Log.d(TAG, "请求头：$headers")
   Log.d(TAG, "body=$jsonBody")

   // ✅ 正确：只记录非敏感的结构化信息
   Log.d(TAG, "请求 ${provider.id} 模型=${model.id} 图片=${hasImage}")
   ```
2. **禁止**把 Key 写入普通 `SharedPreferences`、文件、数据库或 `BuildConfig`。
3. **禁止**新增任何与 AI 请求无关的网络行为：统计 SDK、广告 SDK、崩溃上报、
   用户行为分析、设备指纹采集，一律不接受。
4. **禁止**新增云端中转服务、账号体系或任何形式的数据回传。
5. **禁止**在单元测试、示例代码、文档中写真实 Key（用 `sk-test-xxxx` 之类的假值）。
6. **禁止**放宽 `allowBackup`，或把截图写入外部存储 / `MediaStore`。
7. 新增 Provider 时，**必须**通过 `ai/net/HttpClient` 发请求（统一 HTTPS 与超时策略），
   不要自行 `new OkHttpClient()` 绕过。
8. 涉及密钥、权限、数据流的改动，PR 中**必须**说明安全影响，并同步更新本文档。

## 安全事件如何上报

如果你发现了安全漏洞（例如密钥可被提取、数据被意外外传、权限被滥用）：

1. **不要直接开公开 Issue**，避免漏洞在被修复前被利用；
2. 通过仓库 **Security → Report a vulnerability** 页面私密上报，
   具体流程与联系方式见 [SECURITY.md](../SECURITY.md)；
3. 请在报告中包含：影响范围、复现步骤、PoC（可脱敏）、以及你的修复建议；
4. 我们会在确认后尽快修复，并在 Release Notes 中致谢（如果你愿意署名）。

一般的隐私疑问、数据流问题不属于漏洞，欢迎直接在
[Discussions](https://github.com/MapleYazuu/Screenshot-AI/discussions) 提问。
